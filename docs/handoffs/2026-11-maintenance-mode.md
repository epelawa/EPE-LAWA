# Maintenance mode rollout

This PR provides a server-side request gate in the main Next app and a primary-administrator control under Settings. The public boolean is read fresh from the database for each gated request. When opted in, any missing/invalid response or timeout fails closed with the maintenance response. Public page requests receive a no-store 503 with `Retry-After` and `noindex`; APIs and mutations receive a no-store JSON 503. `/admin` and its descendants retain their existing staff authentication. Only the maintenance illustrations, logo and Next static assets are exempt; this is not a database, Supabase API, direct asset, separate-host or previously cached content access-control system. Verify CDN behavior, alternate deployment URLs, static caches, direct database access, server actions and all configured hosts before relying on it as a security barrier. Never use it to protect private data.

The four original AI-generated illustrations were inspired by the supplied references and recolored for EPE LAWA. They are selected randomly per page response; selection may repeat. The page avoids JavaScript and works without animations.

## Safe activation (not performed by this PR)

1. Review and rehearse `20261121120000_maintenance_mode.sql` on a production-equivalent isolated database and verify a restorable backup. The current production migration ledger has drift and Supabase branching was previously unavailable. Do not bulk-replay migrations.
2. Apply the reviewed migration as a separate forward-only migration, verify boolean RPC permissions, staff authorization, expected revision and audit behavior. It defaults to off. Confirm production `staff_roles_authorized`, `staff_profiles.must_change_password`, `audit_event` and grant behavior match the SQL assumptions. Test with isolated accounts, not production test data.
3. Set server-side `MAINTENANCE_GATE_ENABLED=true` on the public app and wherever the administrative app is deployed, then redeploy. Until opted in, the gate is disabled and Settings reports the control unavailable. The public deployment also needs the existing public Supabase URL and anon/publishable key. Admin needs its existing staff configuration. Opt in only once the migration is ready: an unavailable database or missing RPC causes the gate to fail closed, taking public routes offline while `/admin` remains reachable.
4. Exercise the on/off control with an authorized verified administrator in a safe environment, test mobile/desktop, GET/HEAD, APIs, server actions, static/CDN paths, login and direct alternate hosts. Verify requests stop reaching protected routes when on and resume when off. Monitor latency and database load: the gate performs one uncached database request per non-exempt request with a four-second timeout.
5. Rollback: turn mode off in Settings first. For emergency recovery, set `MAINTENANCE_GATE_ENABLED=false` and redeploy the public app, then diagnose the database. That switch disables enforcement entirely. Migration removal is not required.

No production migration, Vercel environment change or activation was made by this PR. The local PGlite tests are simplified and do not replace Supabase/RLS/authenticated end-to-end checks. The standalone admin deployment must receive its own setting and equivalent configuration.
