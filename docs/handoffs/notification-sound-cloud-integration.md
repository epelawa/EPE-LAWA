# Notification sound and cloud integration

The public site's shared masthead uses the homepage styling on public, member, article, and auth pages. The separate private staff shell remains separate. Member dashboard controls remain in a secondary toolbar.

Sound is opt-in per browser/device. The member notification screen and radio reminder settings offer an enable/test button. Radio reminders can trigger the sound only while the site is visible. A future cloud messaging adapter can signal an actually received foreground notification by dispatching `new CustomEvent('epelawa:notification-arrived', { detail: { type: 'epelawa:notification-arrived', id: '<opaque-event-id>' } })` on `window`; a service worker can instead post the same `{type,id}` to visible clients. IDs must match `[a-zA-Z0-9_-]{1,128}`; no message contents or personal data are needed. The listener checks the per-browser preference, visible state and in-page duplicate IDs. It neither registers a service worker nor sends, receives or authenticates cloud messages by itself.

Browser autoplay, silent modes and OS settings can prevent audio. Service workers cannot play Web Audio in the background, and web push sound is controlled by the browser/OS. No WhatsApp-style background-sound guarantee is possible on the web. Cross-tab deduplication and an authenticated actual provider integration remain to be designed/tested. Do not enable the dormant push prompt or claim push delivery until the provider, subscription, permissions, authentication, worker lifecycle, recipient isolation, privacy and end-to-end delivery are implemented and tested.
