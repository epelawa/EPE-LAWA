# Custom Auth email: implementation status and cutover

The owner requested custom branded email using Vercel environment variables. The new `/api/auth/send-email` endpoint is a **candidate**, not enabled or deployed. It verifies Supabase's Standard Webhooks signature and five-minute timestamp, bounds request size, renders signup, recovery, invite, magic link, reauthentication, and both email-change messages, and sends via Resend with a stable idempotency key. It fails closed on missing configuration, unrecognized actions and provider failure. It does not log payloads, tokens, recipient addresses or provider errors. Tests use synthetic messages and a mocked provider, not real delivery. This endpoint is for Supabase Auth email, not newsletter or contact intake.

Production Auth mail remains unchanged. The Supabase connector's `update_auth_config` does not expose send-email hook settings, and Vercel rejected attempts to create branch-scoped preview placeholders because the current Git branch does not exist in its connected repository yet. No Vercel variables were created by those calls. No placeholder replaced an existing production key. Never enable the production hook with placeholder values: that would break account emails.

Before enabling: review all Auth email types and redirect origins, test actual payloads in an isolated Auth project, provision a verified Resend sender and key, install `AUTH_EMAIL_FROM`, `RESEND_API_KEY`, and a matching `AUTH_EMAIL_HOOK_SECRET` securely in Vercel without sharing values in chat, deploy, configure the Send Email Hook in Supabase using the same signing secret, and verify signup, recovery, invitation, email change and failure behavior including actual inbox delivery. Coordinate rollback to built-in delivery. The hook replaces Auth's built-in email delivery when enabled; disabling email auth would instead break login and is not the desired cutover. Connector access may require the owner to set the hook in the Supabase dashboard. Do not use a production project as a test target for synthetic accounts or alter real accounts without a safe test plan.

The newsletter and contact flows remain separate and incomplete, including mailbox confirmation, anti-abuse, monitored delivery, privacy and reliable persistent intake. No claim of sent email or working forms is supported by the synthetic tests.

## Gmail option and preview placeholders

Gmail SMTP is now supported for the Auth hook using TLS to `smtp.gmail.com:465`, `AUTH_GMAIL_USER` and `AUTH_GMAIL_APP_PASSWORD`. Gmail is selected when both are present. A partial Gmail configuration fails closed; if both are absent, a configured `RESEND_API_KEY` selects Resend. SMTP failure is not automatically retried with Resend because an SMTP timeout can happen after message acceptance. SMTP does not have Resend's provider idempotency guarantee: hook retries or partial multi-recipient sends can cause duplicate mail, and this requires review before activation. Transport tests mock both providers; no actual connection or delivery has been verified.

Vercel now contains deliberately non-working placeholders for `AUTH_EMAIL_FROM`, `AUTH_EMAIL_HOOK_SECRET`, `AUTH_GMAIL_USER`, `AUTH_GMAIL_APP_PASSWORD` and `RESEND_API_KEY` scoped only to the `arena/179404da-epe-lawa` preview branch, created after the branch was pushed. This supersedes the earlier note about rejected placeholder creation. These values do not configure production or send mail. Replace through Vercel settings; do not share credentials in chat. When choosing Resend, remove both Gmail variables rather than leaving placeholders, or Gmail will remain selected. Changing environment variables requires a fresh deployment. The Supabase Auth hook still needs explicit dashboard configuration and an identical signing secret; do not activate against invalid placeholders.
