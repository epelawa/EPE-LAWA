## Requested delivery components and limitations

- The owner's unmodified original logo is `frontend/apps/main/public/brand-logo.png`. The icons and share card resize the whole source proportionally on an ivory background. The original image itself includes third-party names/contact details supplied in the artwork; these are not used as the security contact. Confirm ongoing rights to every element of the supplied artwork before public launch.
- Main and news have custom 404, error-boundary and global-error UI with retry/home actions. Next.js may have already streamed a response before an error boundary renders, so a rendered error screen alone is not proof of HTTP 500. Admin deliberately stays a closed 503 route rather than exposing a login or dashboard.
- `/status/200` and `/status/[400–599]` are **noindex status-reference endpoints** returning the requested HTTP status and a retry button. They are not actual health checks and do not automatically wire every real error to the reference route. 1xx, redirects and no-content statuses such as 204/304 cannot be represented as ordinary HTML responses; no fake redirect or body was added. Future routes must return their real status and select their appropriate error presentation.
- The main-site connectivity toast uses browser online/offline signals and a real same-origin availability check. It reports “Checking for updates…” while checking, then “You’re now online” after a successful reconnection probe. It never claims a data sync completed. Touch pull-to-refresh makes a real probe and requests a router refresh; the retry icon is keyboard-accessible and named. There is **no service worker**, offline page cache or background sync. Browser/device touch, screen-reader and live-network testing remain necessary; automated tests cover the pure gesture/probe logic only.
- All three apps receive baseline response headers. The main site's public CORS header uses the owner-selected public origin rather than `*`; Vercel/CDN behaviour must be checked after deployment. `backend/packages/http-security` adds tested exact-origin CORS and CSRF primitives, but **no state-changing application endpoints exist or are wired to them**. Token generation, host-only cookie issuance, session binding/rotation, preflight method/header checks and end-to-end tests remain required before enabling cookie-authenticated mutations. CORS is not CSRF protection.
- No database schema change was needed for these delivery/audit changes. On 2 November 2026 the production migration history listed only `20261102133703_staff_access_foundation`, matching the local migration. No new migration or data was applied, and no provider settings were changed.

## Local verification

`pnpm install --frozen-lockfile`, `pnpm build`, `pnpm typecheck`, `pnpm test` and `pnpm audit` were run locally. Tests inspect real local HTTP responses for metadata, headers, 404s, sitemap, robots, icons, security.txt, status references and admin fail-closed behaviour; additional tests cover origin/CSRF primitives and connectivity decisions. A separate preview build was checked for noindex/disallow/empty sitemap. Automated tests do not prove security, accessibility, mobile gesture behaviour, actual cache/CDN behaviour or live deployment; run the owner's scans again only after approval and deployment. A headless Chromium attempt could not start because the sandbox lacks `libnspr4.so`, `libnss3.so` and `libnssutil3.so`; real-browser offline, retry, pull, 500-boundary and screen-reader testing is still outstanding.
