# EPE LAWA — Staff Access Foundation

**Status:** Foundation migration applied on production; applications and access flow remain incomplete and are not production-ready.\
**Prepared:** 2 November 2026

## What exists

- `backend/packages/auth` implements a fail-closed entry check requiring a verified identity and an explicit active `admin.access` grant on each check. It does not grant editorial, settings, media or staff-management permissions.
- `backend/supabase/migrations/20261102133703_staff_access_foundation.sql` is an applied migration for an inactive-by-default staff profile and a single explicit entry capability. RLS permits an authenticated user to read only their own profile and, when active, their own entry grant. Anonymous and authenticated roles have no insert/update/delete grants on these tables. No accounts or grants are seeded.
- `frontend/apps/admin/lib/supabase-access.ts` is a server-only, currently unwired adapter: it verifies a supplied token through Supabase Auth and checks the profile/grant using the caller's RLS-scoped identity. It accepts a publishable/legacy anon key only, rejects secret/service-role keys and HTTPS-insecure provider URLs, and fails closed on errors. Its environment names are `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`; no real values are provided or required for a build.
- The same adapter now includes an **unwired**, per-request Supabase SSR session gate. It uses Auth `getUser()` for verification and the caller-scoped client for the active profile/grant, with no-store provider requests. Session-cookie writes require a fresh request/response adapter, enforce host-only `__Host-` cookies with `Secure`, `HttpOnly`, `SameSite=Lax` and `Path=/`, and pass no-store headers. A failed cookie write denies access. It is not a login, route guard, browser client or complete session flow; callers must preserve all cookies and headers on the actual response and set no-store even when no cookie is written.
- A further **unwired experimental read-only route-response adapter** (`respondToAdminRead`) stages session-cookie updates, checks the gate before invoking a synchronous response callback, applies no-store headers and copies all staged chunks to the returned response. Denied sessions do not invoke the callback; response/cookie-copy failures return a generic 503. It does not implement login, Proxy request-cookie propagation, resource-specific authorisation or a mutation guard. It must never be used for mutations: a response failure cannot undo side effects. Real provider, deployed Next.js and browser behaviour require testing and review before any route uses it.
- `safeAdminRedirect` in the auth package is an **unwired** conservative redirect-path primitive. It allows only exact, explicitly supplied literal paths, with `/` as a fallback; it rejects encoded, external, query/fragment and dot-segment inputs. Actual admin routes and Supabase Auth/recovery redirect configuration are not yet approved or connected. This helper does not establish identity or permissions.
- The owner selected email and password for staff sign-in. An **unwired** `signInAdminWithPassword` helper stages session cookies until provider-verified identity and the active entry grant pass, then applies host-only security flags; failed issuance attempts best-effort local session revocation and returns a generic denial. It is not an endpoint or a complete login. It does not enforce rate limiting, CSRF, recovery, MFA, audit, atomic response writes or real-provider/session tests. A future caller must discard the entire response on cookie-write failure; partial response writes are not transactional. No production accounts, configuration or data were changed.
- `signOutAdminSession` is an **unwired** logout helper. It attempts local-session revocation with Supabase and independently clears host-only admin cookie chunks; it reports failed provider revocation and failed cookie writes separately. It is not an endpoint, does not revoke all sessions and still needs CSRF, response wiring, audit and real-provider/browser tests.
- The admin app continues to return HTTP 503 with `no-store` and `noindex`. There is no sign-in form, session/refresh flow, account bootstrap, audit trail, role-management UI or protected dashboard. Do not remove this fail-closed behaviour until those controls and real provider integration tests are complete.

## Verification and limitations

- Automated unit tests cover invalid tokens, failed verification, missing/revoked grants and upstream errors. Mocked adapter tests verify Auth is called before RLS-scoped reads and that secret keys/insecure URLs fail closed. These mocks do **not** prove Supabase Auth or production configuration works.
- Mock-provider tests exercise password sign-in success, invalid credentials, provider failure, mismatched identity, inactive/revoked access, Auth/database errors, invalid provider configuration and failed response writes; they do not test real Supabase or browser behaviour.
- Session-gate tests use in-memory synthetic cookies and mocked HTTP responses to exercise verification order, absent/malformed/invalid sessions, inactive and revoked staff, provider failure, refresh, cookie flags and failed cookie writes. They do **not** test a real Supabase Auth session, Next.js response cookie propagation, real browser behaviour or real-provider security. No persistent fixture or user was created.
- An isolated synthetic test uses real Next.js request/response objects with mocked Supabase Auth/RLS. It checks response cookie flags and chunk propagation, no-store override, revoked and unconfigured denials, and generic failure when a response or cookie write fails. It is not an HTTP route, browser, concurrency, CDN, or real Supabase integration test. The callback is deliberately synchronous and read-only, and no actual admin route invokes it.
- A test runs the local SQL against an ephemeral in-memory Postgres-compatible PGlite instance with synthetic test-only identities and simulated Supabase roles/`auth.uid()`. It checks empty starting tables, own-row isolation, inactive/non-staff denial, write denial and revocation. No application database is seeded. This is useful local evidence, **not** a substitute for testing real Supabase Auth, grants, RLS and service-role behaviour.

## Session implementation reference

Supabase's [SSR client documentation](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs) describes request-scoped cookie clients, verified user claims and the need to preserve refreshed cookies and no-cache headers. This helper uses `getUser()` for server verification; it does not rely on unverified `getSession()` data. Next.js proxy/route wiring, sign-in, sign-out, recovery, CSRF, redirects and real-browser refresh handling remain unimplemented and require review before enabling admin.
